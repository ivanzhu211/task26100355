# planadjust

门店销量预测的人工调整与层级分摊库。由上层补货计划服务以库的形式调用（无接口层），
数据持久化在 SQLite。一个 `Planner` 实例对应一个门店；各门店计划互相独立。

## 模型

- 计划期固定 91 天（13 个自然周，从周一开始），最小格子为 一个 SKU 的一天，值为非负整数。
- 每个 SKU 属于一个品类；商品维度（全部 > 品类 > SKU）与时间维度（计划期 > 周 > 天）
  各自构成树形结构。
- 统计预测由别的模块给出，每格一个非负整数，通过 `ReplaceForecast` 整版更换。
- 一条调整 = 商品维度 × 时间维度的任意组合，语义为"该范围合计等于目标值"。

## 分摊规则

任何时刻，计划值 == 从当前统计预测出发、按提交先后依次应用所有**生效**调整的结果。

应用一条调整时：

1. 被新范围完全包含的更早生效调整，其格子原样不动；剩余量（目标 − 冻结部分合计）
   按其余格子当前值比例分摊，采用最大余数法：每格拿精确份额向下或向上取整的值，
   合计分毫不差；这些格子当前全为 0 时平均分。
2. 若有更早的生效调整完全包含新范围，其合计保持不变：新范围的增减量由**最近**的
   包含者消化——只动包含者范围内、新范围之外、也不在其他更小生效调整里的格子，
   按当前值比例反向消化。
3. 新调整与生效调整相交但互不包含 → 旧的作废；范围完全相同 → 旧的被取代。
   作废/被取代的调整不再影响任何格子。

调整无法满足（目标小于冻结部分合计；反向消化的格子不够减；有量要分摊或消化却没有
能动的格子）时，提交被**原子拒绝**：计划值与所有调整状态都不变，本该作废的也不作废。
可行性按交叉调整作废之后的计划判断。重算（撤销/作废/更换预测触发）时才发现无法满足
的旧调整被标为**冲突**、不再生效，其余照常。

调整状态：`生效 / 作废 / 被取代 / 冲突 / 已撤销`。

## API

```go
p, err := planadjust.Create(path, planadjust.Config{StoreID: "s1", SKUs: defs})
p, err := planadjust.Open(path)                 // 重启后恢复：计划值、调整及状态完全一致
id, err := p.Submit(scope, target)              // err == planadjust.ErrInfeasible 表示被拒绝
err := p.Undo(id)                               // 撤销一条生效中的调整
err := p.ReplaceForecast(map[string][91]int64)  // 整版更换统计预测
sum, err := p.PlanSum(scope)                    // 任意范围调整后合计
sum, err := p.ForecastSum(scope)                // 任意范围统计预测合计
v, err := p.PlanValue(sku, day)                 // 单格查询
adjs := p.Adjustments()                         // 全部调整及状态
```

上层保证同一门店同一时间只有一个操作，因此 `Planner` 内部不加锁。

## 实现要点

- 生效调整集始终是层叠（laminar）族：提交时相交但互不包含的旧调整即作废，
  因此任意两条生效调整要么嵌套要么不相交，分摊/消化规则由此简化。
- 不变量：每条生效调整被应用后，其范围合计恒等于目标值（包含它的调整通过反向
  消化保持它的合计，被它包含的调整只动自己的格子）。
- 不会引起作废/取代的提交走增量路径，直接在当前计划上应用；其余情况（撤销、
  作废、更换预测）从预测出发全量重放。
- 可行性只取决于目标值与生效集结构（与预测取值无关），因此提交时的可行性
  判断与重放结果一致；冲突路径作为防御性安全网保留。
- 每次状态变更在同一事务内落盘（预测、计划值快照、全部调整及状态）。

## 性能（满规模实测，Apple Silicon）

5000 SKU、60 品类、45.5 万格子、500 条生效调整（53 条覆盖整品类/整周/全期）：

| 操作 | 要求 | 实测 |
| --- | --- | --- |
| 任意范围合计查询 | < 50ms | ~0.3ms |
| 提交（不引起作废） | < 2s | ~16ms |
| 撤销/更换预测引起的重算 | < 30s | ~1.9s |
